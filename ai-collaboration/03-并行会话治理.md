# 03 · 并行会话治理

> 这一篇讲的是最容易造成**不可逆损失**的一类问题：多个 AI 会话 / 工具同时操作同一个工作区。

第 02 篇的桥梁文件解决的是"两个 AI 知道彼此在做什么"。但还有另一种情况：

**同一个工作区，被不同的 AI 工具（IDE 插件、CLI、网页版）在**不同的时间**打开并操作，而这些会话之间完全没有通信。**

这种情况下，桥梁文件也救不了你——因为某个工具可能正在做**版本控制层面**的操作。

---

## 一个真实的事故

### 现象

某天用户反馈："让某个 AI 编辑器做了改动，项目变成之前某个未修改的版本了。"

进入工作区后看到的第一个异常：

```
git status  →  83 个文件显示为 D（已删除），但工作区文件看起来是"干净"的
```

紧接着：

```
git status  →  fatal: not a git repository
```

**.git 目录本身已经被删除了。**

### 根因（从 reflog 还原出来的时间线）

```
12:07:41  在 feature 分支上提交了一个检查点
12:07:42  checkout: moving from feature → main        ← 切分支
12:25     .git 整体被移入回收站
```

三个前提条件叠加，才造成了这次事故：

| 前提 | 说明 |
|---|---|
| **① 主分支长期未合并** | `main` 停在几天前，feature 分支上积累了全部新工作，两者差距巨大 |
| **② 工作一直在 feature 分支上做** | 从没有人把成果合并回 `main`，所以 `main` 是一个"看起来很旧"的分支 |
| **③ 某次操作切换到了 `main`** | 切分支 = **工作区被整体替换成旧版本** |

**关键认识：切分支不是"看一眼旧版本"，是"把工作区文件全部换掉"。**

那个 AI 编辑器的行为完全合理——它切了分支，工作区就变成了分支的内容。问题在于**没有人知道即将发生这件事**，也没有人意识到 `main` 落后了 40+ 个提交。

### 为什么"看起来很干净"反而更危险

`git status` 显示 83 个文件是 `D`（删除）而工作区看起来正常——这个组合意味着**工作区的内容已经和 HEAD 不一致了**，只是恰好文件还在（被换成了旧版本的内容）。

**判据（能救命的一张表）**：

| `git status` 显示 | 含义 | 处理 |
|---|---|---|
| 大量 `A`（新增，全部文件） | git **没读懂** ref（编码/格式损坏） | 修 ref 格式 |
| 大量 `D`（删除） | ref 指向了旧的提交 | 检出到正确提交 |
| 若干 `M`（修改） | 工具真的改了文件 | 比对内容 |

**这张表的用法**：出现异常时，先看 `status` 的第一列字母，它直接告诉你问题在哪一层——**是版本控制元数据坏了，还是文件内容被换了**。

### 恢复过程（值得知道的逃生通道）

`.git` 被删后，常规手段全部失效。实际走通的路是：

1. **先找回收站**——但要注意：回收站里的 `.git` 可能是**空壳**（本次就是：只有 32 个文件、`objects` 全是空目录）。**直接还原它没用。**
2. **不要依赖回收站的路径元数据**——它记录的原始路径可能被截断（本次：38 位对象哈希只剩 22 位），无法据此重建目录结构。
3. **改为暴力扫内容**：遍历回收站所有实体文件，逐个尝试 zlib 解压，解压后内容形如 `b"<blob|tree|commit> <size>\x00..."`，再对内容算 SHA-1 与文件名（对象名）比对，命中即收集。

```
结果：13911 个候选文件 → 识别出 2086 个有效 git 对象
      （1548 blob / 473 tree / 64 commit / 1 tag）
      目标提交及整条祖先链全部命中 → 43 个提交完整恢复
```

4. **重建仓库**：对象按 `sha[:2]` 建目录、`sha[2:]` 作文件名写入；写 ref；`git fsck` 校验；检出到工作区。

**两个容易翻车的细节**：

- **写 ref 文件必须用 ASCII 编码**。带 UTF-8 BOM 会让 git 读不了 ref，报 `has trailing garbage`；
- 更隐蔽的后果：ref 读不了时，git 认为分支不存在，**下一次提交会写成一个没有父提交的 root commit**——表现为 `git status` 突然显示全部文件为 `A`（即上面判据表的第一行），**40 多条历史瞬间失去连接**。

> **教训**：写 ref 一律用 `ascii`，不要用 `utf8`。这个坑值 40 个提交。

**最终结果**：零损失恢复。

**但要说清楚——这次能救回来是运气好**，具体是三个条件同时满足：回收站没被清空、对象文件没被覆盖、且我们有能力识别它们。**大多数情况下没有这么幸运。**

## 预防：三条能真正避免事故的纪律

### 纪律一：一个工作区，同时只有一个"写者"

这是最根本的一条。

```
❌ 编辑器 A 在改 src/          ┐
   编辑器 B 在改 src/          ├─ 同时 → 必然出事
   CLI 工具在跑 git 操作       ┘

✅ 同一时刻，只有一个工具对工作区有写权限
```

**判断标准**：如果某个操作可能改变**工作区的文件内容**或**版本控制状态**，它就是"写者"。切分支、检出、重置、批量删除——**全部属于"写者"行为**。

### 纪律二：主分支不能长期落后

这次事故的真正温床是"`main` 停在几天前 + 全部工作在 feature 分支"。

**规则**：**每完成一个可交付的里程碑，就合并回主分支。** 宁可合并得频繁一点，也不要让某个分支领先几十个提交。

好处有两个：任何一次切分支的破坏半径更小；任何时刻的 `main` 都是一个能跑的版本。

### 纪律三：定期做整包快照

版本控制是"多点备份"最可靠的形式，但仓库本身是单点。项目里的做法是：

```bash
# 完整快照，含全部提交与标签，单文件
git bundle create backup/full-<date>.bundle --all
git bundle verify backup/full-<date>.bundle   # 验证："records a complete history"
```

**为什么用 bundle 而不是复制目录**：bundle 是**单个文件**（体积接近仓库本身），可以直接丢到网盘/U 盘；恢复就是 `git clone <bundle> <目录>`，能完整还原历史与标签。

**做到什么频率**：每天收工时一次。成本几秒钟，代价是你不会因为一次误操作损失一周。

## 附：环境层面的坑（Windows 中文路径）

这一节内容偏环境，但**排查成本极高**，所以值得单列。

| 现象 | 根因 | 规避方式 |
|---|---|---|
| Shell 工具全线报 `command not found` | Shell 的 PATH 环境损坏 | 改用别的 shell / 直接调可执行文件的绝对路径 |
| Shell 执行成功但**没有任何输出** | 输出捕获失败 | **把结果写到文件，再用文件读取工具读** |
| 含中文的路径下 git 命令解析失败 | 编码不匹配 | 用 `--git-dir=<绝对路径>` 形式，或用脚本语言直接指定工作目录 |
| 含中文的路径下编辑器修改"报成功但没写入" | 编码问题导致的静默失败 | **改用整文件重写，重写后必须用搜索工具复核** |
| 输出重定向到文件变成二进制 | 编码判定错误 | 让脚本语言以 UTF-8 显式写文件 |

**最重要的一条**：**"命令执行成功但没有输出"和"命令没有执行"是两回事。** 前者会让你误以为一切正常，然后基于错误的前提继续工作。

**通用规避模式**：

```
执行（不管输出） → 结果写入 UTF-8 文件 → 用文件读取工具读
```

这个模式虽然笨，但在输出通道不可靠时是唯一可靠的做法。

---

## 小结

> **并行会话的风险不在于"AI 改错代码"，而在于"AI 改变了工作区的状态，而你不知道"。**
>
> 三条纪律对应三种保证：**一个写者**（避免同时改动）、**主分支不落后**（缩小破坏半径）、**定期快照**（保证可恢复）。
>
> 最后一条听起来最笨，但它是唯一一条在事故真的发生时会救你的。
