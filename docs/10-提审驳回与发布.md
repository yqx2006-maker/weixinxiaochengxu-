# 10. 提审、驳回、发布

> 这一节是我们唯一一次被驳回的完整记录，加上提审和发布的操作细节。驳回不可怕，可怕的是驳回后乱改一气——我们第一反应就乱改了，这一节有完整教训。

## 10.1 提审：交什么、等多久

**入口**：mp 后台 → 版本管理 → 开发版本 → 「提交审核」。

- **版本说明写人话**："修复保存图片失败的问题；新增发帖带图"。别写"优化了若干体验"——审核员也是人，说清楚改了什么能减少误会；
- **时效**：官方说法 7 天内，实际通常 1~2 天，快的几小时；赶上节假日会慢；
- **加急**：审核页有加急入口，每月有次数限制，真急再用。

## 10.2 一次驳回的全记录（原文保留）

**收到什么**：一条驳回，理由只有一句——

> 「设置的图片保存到手机相册，仅设置用户可以看，不属于社交，建议移除整改后，再去提交审核呢」

没有指明哪个页面、哪个功能。

**我们第一步就做错了**：把项目里**全部 6 处分享入口**都删了（8 个文件、10 处改动），理由是"过审优先"。包括转发小程序本身的 `onShareAppMessage`。

**后来发现删多了**：再提审时，平台页面提示"确保在小程序代码中正确调用了 onShareAppMessage 或 onShareTimeline 以启用分享功能"——原来**转发小程序本身是微信基础能力，平台不但不禁止，还主动提醒你定义它**。真正踩线的只有一类：**把用户生成的图片直接发到聊天**那种内容分发。

**最终改回**：恢复 4 处"转发小程序本身"（首页/任务/出片/我的），保持移除所有"分享用户内容"的入口。过程中还澄清了一个误解：代码全删后右上角菜单里的"转发"仍显示（灰色），这不是没删干净——**未定义转发函数时该项自动置灰，这就是"关闭分享"的标准效果**，客户端固定菜单删不掉。

**沉淀下来的判断准则**：

> **转发"小程序本身" = 基础能力，保留；转发或直发"用户产生的内容" = 社交分发，没有社交类目就不要留。**

## 10.3 驳回的通用应对法

| 步骤 | 做什么 |
|---|---|
| 1. 读理由 | 常常就一句话，没指明位置——正常，别等它说清楚 |
| 2. 自己定位 | 全项目搜关键词：分享、支付、定位、生成、评论……把可疑入口列成清单 |
| 3. 分类 | 判断踩线的是哪类能力：类目不符？隐私声明没对齐？内容分发？还是权限？**不同类的改法完全不同** |
| 4. 最小改动 | 只改踩线的那类。顺手"多删点保险"是这次教训里最贵的一步 |
| 5. 重新提审 | 改完直接提。来回两轮很正常，心态按"流程"处理，别按"事故"处理 |

## 10.4 通过之后：发布与更新

**审核通过 ≠ 上线**。要去 **版本管理 → 审核版本 → 「发布」** 手动点，用户才能用到。

- 发布后几分钟到几小时内全量生效；
- 不想一次全放开，有**分阶段发布**（按比例放量），个人项目一般用不上但知道有；
- 发出去的版本发现问题，后台支持**版本回退**——这算是最后一道保险，但别把它当日常手段；
- 之后的更新就是循环：改 → 上传 → 提审 → 通过 → 发布。**每次更新前真机走一遍主路径**，这条在所有环节里性价比最高。

（大白话：审核通过只是"考过了"，还得你自己去领证。忘了点发布，用户那边永远停留在旧版本——这是我们幸好没踩过、但见过别人踩的坑。）
