# 05 · 提示词设计：让 AI 输出能直接进代码库

这一篇讲的是**让模型产出结构化、可校验、能直接入库的内容**。不是"怎么写 prompt 让回答更好"，而是"怎么让输出可以被程序消费"。

场景：你要让模型生成一组条目（行程 / 清单 / 方案 / 任务），每条包含若干字段，其中一部分字段要展示给用户。

---

## 三个原则

### 原则一：要 JSON，就要把形状给全

只写"请返回 JSON"没有用。模型需要知道四件事：

| 要素 | 例子 |
|---|---|
| **字段名** | `guide.first` —— 用英文、语义明确 |
| **类型与形状** | 嵌套对象、数组、可选字段都要标 |
| **长度约束** | "30-60 字" 比 "简短一些" 可执行 |
| **示例值** | 给一个完整示例对象 |

**一个容易被忽略的点**：数组元素个数也要写死（"生成 6 条"），否则你会拿到 3 条或 11 条。

---

### 原则二：能枚举的，就不要让模型自由发挥

这是本篇最有价值的一条。

**反例**：

```
"请在每条内容里描述画面的构图方式"
```

模型会写出「两人背影入画」「主体偏左」这类自然语言。然后你的前端需要**用关键词去反推**它说的是什么类型 —— 而关键词规则永远覆盖不全：

- "左侧" 不等于 "偏左"
- "两人入画" 你根本没写进规则
- 结果：**所有条目都落到默认值**，界面上一模一样的示意图

**正解**：

```
"frameType": "string，从以下 9 个值中选一个：
  centered | left_right | two_people | side_subject | top_area |
  bottom_fill | leading_lines | close_up | rule_of_thirds
  注意：不要每条都用同一个值"
```

**判据**：如果一个字段的取值空间是有限的，**就把它写成枚举**。

**为什么"不要每条都用同一个值"这句必须加**：模型有强烈的倾向性（喜欢选第一个或最"安全"的那个）。不加这句，你大概率会拿到清一色的同一个值。

**并且要做双轨兜底**：

```
① 模型声明的枚举值（最可靠）
      ↓ 缺失时
② 关键词推断（作为兜底，规则要宽于你的预期）
      ↓ 仍失败
③ 默认值
```

枚举是主路径，关键词只是保险。**不要让关键词成为主路径** —— 那等于让下游去猜上游的自然语言。

---

### 原则三：让模型做只有它能做的事

模型有些优势是人没有的：它知道大量地点/领域常识，能快速产出结构化知识。

所以提示词里应该明确：**哪些部分靠它的知识，哪些部分是硬约束。**

```
## 你可以自由发挥的
- 每个条目的具体名称（选该地点真实存在、有代表性的）

## 硬约束（必须遵守）
- 不得出现任何需要现场测量才能确认的数字（如"走 50 米""第 3 棵树"）
- 不得出现专业术语
- 每条的名称必须能被检索到（用官方名称，不要自创简称）
```

**最后一条尤其重要**：如果名称会用于后续的检索/定位，**必须要求用可检索的官方名称**。自创的简称会让下游查询命中错误结果。

---

## 完整骨架（可直接改造）

```
你是<角色描述>。根据给定条件生成 <N> 条<条目类型>。

## 输入条件
- 地点：{place}
- 风格倾向：{style}
- 同行人数：{people}

## 输出格式
严格输出 JSON 数组。不要 markdown 代码块，不要任何解释文字。

[
  {
    "id": "string，英文短标识，全局唯一",
    "name": "string，条目名称，8-12 字，必须用可检索的官方名称",
    "poiName": "string，用于地图检索的名称，与 name 相同或更完整",
    "reason": "string，为什么选它，20-30 字",
    "steps": [
      {
        "title": "string，动作名，6-8 字",
        "desc": "string，具体做法，30-50 字，只给动作不给形容词",
        "tags": ["string，2-4 个标签，每个不超过 6 字"]
      }
    ],
    "guide": {
      "first": "string，第一步做什么，20-60 字，必须是一条能直接照做的指令",
      "easy": {
        "site": "string，站在哪里，必须包含可数锚点（入口/桥/转角/尽头等）",
        "when": "string，什么时候来，含具体时段",
        "how": "string，怎么拍，不含任何专业术语",
        "goal": "string，拍成什么样算合格，给一个够得着的最低标准"
      },
      "pro": {
        "site": "string，换个位置到哪",
        "frame": "string，画面里多什么少什么",
        "light": "string，什么时候光影变化最大",
        "exposure": "string，点哪里、调什么"
      }
    },
    "viewType": "string，从以下 9 个值中选一个：centered | left_right | two_people | side_subject | top_area | bottom_fill | leading_lines | close_up | rule_of_thirds。不要每一条都用同一个值"
  }
]

## 内容约束
1. `steps` 必须正好 3 条；`tags` 必须 2-4 个。
2. `guide.first` 与 `guide.easy.site` 不能是同一句话。
3. `easy` 面向随手拍的人：不含任何专业术语；`pro` 面向想认真拍的人：不含具体相机参数（不要光圈/快门/ISO/焦段/白平衡）。
4. 两版是**递进**关系，不是同一句话换措辞说一遍。
5. 绝不编造距离、数量、序号类信息（"走 50 米""第 3 棵树"）。
6. 所有时段、开放信息以官方口径为准；不确定就不写，不要猜。

## 反面示例（不要这样写）
- ❌ "注意三分法构图"            —— 用了目标用户看不懂的术语
- ❌ "往西走约 50 米"             —— 编造了需要现场测量才能确认的数字
- ❌ "站在堤边"                  —— 这个方位在任何位置都成立，无法执行
- ❌ easy 与 pro 都是"站在柳枝旁" —— 两版撞句，其中一个等于没写
```

## 分两步生成：整批 + 按需补全

一次性生成全部内容会遇到两个问题：**输出太长会被截断**、**模型对后面几条的注意力下降**。

**做法：拆成两条链路。**

### 链路一：整批生成（粗）

一次生成全部条目，字段可以**只填必须的那部分**，允许其他字段留空。

### 链路二：单条按需补全（细）

当用户真的打开某个条目时，再**按需**为这一条生成完整内容。

```ts
// 关键设计
const inflight = new Map<string, Promise<void>>()   // 同一个条目并发只补一次

async function enrich(item) {
  const key = `${item.id}|${item.name}`             // ← key 必须包含名称
  if (inflight.has(key)) return inflight.get(key)

  const task = (async () => {
    try {
      const data = await callAI(buildSinglePrompt(item), { timeout: 8000 })
      Object.assign(item, data)                     // 写回
      persistRoute()                                // ← 只持久化"补到的内容"
    } catch { /* 失败就保持原样，页面显示本地派生内容 */ }
    finally { inflight.delete(key) }
  })()

  inflight.set(key, task)
  return task
}
```

**三个坑都在这段代码里，逐条说**：

| 坑 | 说明 |
|---|---|
| **去重 key 只用 id** | 如果 id 是 `ai_0` / `gen_0` 这种**批次内序号**，跨批次会撞号，并发补全时两个不同条目互相覆盖。**key 必须含名称** |
| **持久化了派生的内容** | 如果把"本地兜底生成的完整内容"也存下来，下次判断"这条缺内容吗"就会得到"不缺"——**按需补全永远不会再触发**。只持久化真正来自 AI 的部分 |
| **没有 in-flight 去重** | 用户快速切换条目会发起多个并发请求，既浪费配额又可能互相覆盖 |

## 七个反面模式

| # | 反面模式 | 后果 |
|---|---|---|
| 1 | **示例与约束矛盾** | 一边写"禁止编造距离"，示例里却有"走 50 米"。**模型学示例，不学规则** |
| 2 | **只在 prompt 里说"简短"** | 模型会给出模糊的长句。要给字数区间 |
| 3 | **要求返回 JSON 但没禁 markdown** | 输出会被 ```json 包裹，解析失败 |
| 4 | **用自然语言描述有限取值** | 见原则二，必然产生"全部落到默认值" |
| 5 | **把长度约束写在最后** | 模型对开头和结尾的注意力最高，**关键约束要放两端** |
| 6 | **一次要求太多字段** | 字段越多，漏字段概率越高。超过 10 个字段考虑拆两次 |
| 7 | **不做长度上限** | 输出变长 → 耗时增加 → 超时概率上升（注意：**这不影响限流**，限流按调用次数算） |

## 调试方法

**第一条：让错误信息带上原始返回。**

```
生成失败。原因：<把原始 errMsg 拼进来>
```

一个小改动，但价值极高 —— 它让你一眼区分"超时"和"限流"：

| 失败 | 原因 | 对策 |
|---|---|---|
| 超时 | 单次耗时太长 | 提高超时上限、缩短 prompt 与输出 |
| 限流 | 短时间调用太多 | 降频 + 给用户"等 X 秒"的提示 |
| 解析失败 | 输出被截断或包裹 | 改容错解析 |

这三者的现象都是"生成失败"，但原因和对策完全不同。**没有原始错误信息，你只能猜。**

**第二条：用脚本核对输出，不要用眼睛看。**

生成 200 条内容，人眼是审不住的。把内容纪律写成断言（见 [`tools/check-copy-discipline.cjs`](../tools/check-copy-discipline.cjs)），每次改完 prompt 跑一遍。

**第三条：改 prompt 后必跑回归。**

prompt 是代码。改一个字都可能影响全部输出。**把它当作代码对待** —— 有版本、有测试、改动后跑校验。

---

## 一句话小结

> **好的提示词不是让模型写得更漂亮，是让它的输出不需要人来收拾。**
>
> 判据很简单：**输出的每一个字段，你的代码能不能直接用它而不需要再猜？**
> 需要猜的地方，就是提示词该改的地方。
