# 01 · 技术选型与取舍

（大白话：这一篇回答"用什么技术做"。结论：官方原生写法 + TypeScript（给 JS 加类型检查，错得早发现得早）+ 腾讯云开发（后端帮你管好）。不用第三方框架的理由在下面。）

## 结论先给

**原生小程序 + TypeScript + CloudBase 云开发，不引框架。**

这个组合不是"最好"的，是**在当前约束下最省事**的。约束是：一个人、5 个工作日、需要交付可体验的完整作品、目标用户是手机端普通用户。

---

## 决策一：原生 还是 跨端框架

| 方案 | 优势 | 在"一个人 + 极短工期"下的实际代价 |
|---|---|---|
| **原生 + TS**（选它） | 无构建步骤，改完直接编译；主包体积可控；官方文档与报错一一对应；AI 助手对原生 API 的准确率明显更高 | 手写更多样板（列表渲染、状态同步）——但这部分恰好是 AI 最擅长写的 |
| Taro / uni-app 等跨端框架 | 一套代码多端；组件生态丰富 | 多一层构建；**框架报错 + 原生报错叠加，排查时间翻倍**；AI 生成的代码经常混淆"框架写法"与"原生写法" |
| 直接用原生 JavaScript | 少一层类型检查 | 页面数据、云函数返回值、本地存储结构全是 JS 对象，改一处漏一处（见下） |

**判断标准**：如果你只做一个平台，跨端框架的收益是 0，成本是正的。这个项目只做微信小程序，所以框架被排除了。

---

## 决策二：要不要 TypeScript

这是本次选型里**回报率最高的一项**，理由不是"类型安全"这种抽象说法，而是具体到它拦住了什么：

1. **本地存储结构漂移**。用户档案、路线、任务进度都存本地，格式一旦不一致，读出来就是 `undefined`，而小程序不会给你任何警告。类型把这类错误提前到编译期。
2. **强制过一遍新字段**。项目中期给数据结构加了一个新字段（每个拍摄建议新增"第一张先拍这个"），设为**必填**。结果编译器一次性报出了所有需要补齐的机位与模板——**这就是"必填"两个字的全部价值**。
3. **云函数返回值的形状**。前端与云函数是两套代码，靠约定通信，没有类型就只能靠猜。

**代价**：需要 `tsconfig.json`，需要理解 `wx.` 命名空间，报错信息偶尔难懂。

**一个务实的折中**：AI 助手写 TS 的准确率并不比写 JS 低，甚至更高（因为类型给了它约束）。所以"用 TS 会增加 AI 协作成本"这个担心，在实际使用中不成立。

> ⚠️ **踩坑提醒**：本地跑单元测试时，Node 默认不认 `.ts`。需要 Node 23+ 才能直接 `require` TS 文件；更稳的做法是让测试脚本把 TS 复制到临时目录再加载（见 [`tools/check-copy-discipline.cjs`](../tools/check-copy-discipline.cjs) 里的 `loadServices()` 做法——它还会顺手补齐无扩展名的相对导入）。

## 决策三：后端怎么做

| 方案 | 结论 |
|---|---|
| **CloudBase 云开发**（选它） | 云函数 + 数据库 + 存储 + AI 能力一套打通，**不需要自己买服务器、不需要备案、不需要处理证书**。关键：**个人主体也能跑通完整链路** |
| 自建服务端 | 需要服务器、域名、备案、HTTPS 证书。在 5 天工期里，这些是纯粹的负收益 |
| 完全不用后端 | 做不了 UGC（用户投稿、评论），也调用不了小程序端不支持的图像模型 |

**但要记住一个界**：云开发很方便，**不代表什么都要上云**。这个项目的划分是：

> **本地存储为主，云端只存 UGC。**

路线、打卡进度、积分、作品全部存在用户设备上；云端只保存用户投稿内容与全局配置。带来三个好处：

1. **隐私面最小化**——用户的旅行记录不出设备，隐私声明可以写得很干净；
2. **离线可用**——断网也能看路线、打卡（打卡照片本来就是本地的）；
3. **成本几乎为零**——读写在用户设备上，不消耗云开发配额。

**代价**：换设备数据不迁移；本地临时文件路径会失效（这个坑见 [第三册 · 数据与状态](../pitfalls/05-数据与状态.md)）。

## 决策四：AI 模型怎么挑

要把**文本**和**图像**分开评估，因为它们的约束完全不同。

### 文本模型

| 评估维度 | 说明 |
|---|---|
| 调用方式 | 能否在小程序端直接调用？需不需要自己管 API Key？ |
| 计费 | 有没有免费额度覆盖开发与演示期 |
| 稳定性 | 限流阈值是多少？超时表现是什么？ |
| 结构化输出能力 | **这是最关键的一项**——它要吐 JSON，不是吐散文 |

这个项目最后走的是**云开发内置的 AI 扩展能力**（`wx.cloud.extend.AI`），因为：不需要在小程序端存 Key、消耗的是平台赠送额度、且与云开发同一套鉴权。

### 图像模型（图生图）

图生图有一组**独有的硬约束**，必须在选型时就查清楚：

1. **小程序端不能直连图像模型**——必须经云函数中转；
2. **必须确认参数契约**：官方文档写的是 `{ model, prompt, images, revise }`，就不能多传 `size`、不能加未文档化的字段（多传不一定报错，但会静默失效）；
3. **必须确认单次耗时**——图生图 20~60 秒是常态，云函数默认超时 20 秒**必然失败**，要显式配置（见 [04 · 云开发与部署](04-云开发与部署.md)）；
4. **必须确认返回格式**——返回的是临时 URL 还是 fileID，直接决定前端能不能保存到相册（这是踩过的坑，详见 [03 · AI 链路接入](03-AI链路接入.md)）。

> **教训**：把"模型能不能用"和"链路能不能通"分开验证。这个项目在选型阶段就确认了模型可用，但真正跑通链路又多花了半天——差的全部在参数契约、超时、返回格式这三件"文档里写了但容易被跳过"的事上。

## 决策五：出片能力怎么做

"生成一张可保存的合成图片"有三条路：

| 方案 | 取舍 |
|---|---|
| **canvas 2d 前端合成**（选它） | 零成本、离网可用、可实时预览。代价：排版全靠手写坐标，调试麻烦（坑见 [第三册 · 画布与图像处理](../pitfalls/04-画布与图像处理.md)） |
| 云函数 + 图像库（如 sharp/PIL） | 排版能力强、可控性好。代价：每次出图都要上传下载，耗时与流量都上去了 |
| 直接调用云端图片合成服务 | 最省事，但引入额外费用与依赖，且自定义排版能力受限 |

**判断依据**：如果排版是确定的（模板固定几个位置放文字和图片），前端 canvas 完全够用，而且**响应速度是云端方案的数倍**——用户点一下就能看到结果，这在"出片"这种强反馈场景里很重要。

## 一度判断错的地方

**我一开始认为应该"多做一点、留着以后用"**——比如把用户数据提前上云、把功能做得更全。

这个判断在 5 天工期下是错的。真正有效的策略是**先把主链路打穿到可演示，再回头补可靠性与内容质量**。项目实际的节奏就是：前两天做出了能跑通的闭环（虽然很脆），后面三天全在补兜底、补内容纪律、补真机问题。

如果反过来先做"完备的基础设施"，极可能到交付时主链路还没走通。

---

## 一句话小结

> **选型的目标不是选最好的技术，是选"失败时你还能修得动"的技术。**
> 原生 + TS 让你能读懂每一层报错；云开发让你不用管运维；本地存储让你在断网时也能演示。
