# 04 · 云开发与部署

这一篇是**照做清单**性质。每一节都对应一个真实卡住过我们的点。

（大白话：云开发 = 腾讯帮你管的现成后端。SDK 版本、超时、密钥、权限、告警，每一样都卡过我们一次，照着这篇逐项勾就行。）

---

## 一、目录结构

```
project/
├── miniprogram/                # 小程序端
│   ├── pages/                  # 页面（每页四件套：ts / wxml / wxss / json）
│   ├── services/               # 服务层：AI、数据、存储、地理
│   ├── components/             # 自定义组件
│   ├── typings/                # 类型定义
│   └── app.json / app.ts / app.wxss
├── cloudfunctions/
│   ├── <fn-a>/                 # 每个云函数是独立部署单元
│   │   ├── index.js
│   │   ├── package.json
│   │   ├── config.json         # 超时等配置
│   │   └── lib/                # 该函数私有的模块
│   └── <fn-b>/
└── project.config.json
```

**关键认知：每个云函数是独立部署单元，不能跨目录 `require`。**

这个项目有两个云函数需要同一份限流逻辑。因为不能跨目录引用，只能**同源复制两份**，并在代码注释里写明"改规则要同步两边"。这是平台约束下的必然结果，不是偷懒——**但要付出代价**：两边不同步就会出现行为不一致，而且很难被发现。

> **替代方案**：如果共享逻辑较多，可以改用构建步骤把共享模块复制进各函数目录，或做成 npm 私有包。在这个项目的规模下（一份 90 行的限流模块），同源复制 + 注释警告是成本最低的选择。

## 二、依赖版本：一个会直接报错的陷阱

云函数 `package.json` 里的 SDK 版本**不是随便填的**。

这个项目踩的坑：图像模型能力依赖新版 SDK，但 `package.json` 里写的是旧版。表现是**云函数直接报错，不是降级**。

```jsonc
// 使用 AI 图像能力时，SDK 有最低版本要求
{
  "dependencies": {
    "wx-server-sdk": "4.0.2"    // 具体版本以官方文档为准，务必查证
  }
}
```

**教训**：接入 AI 能力前，先看官方文档的**前置要求**章节。这类"版本不够直接崩"的约束，文档一定写了，但它通常不在你正在读的那一页。

## 三、超时配置：默认值几乎总是不够

| 场景 | 需要的时间 | 默认 20s 的结果 |
|---|---|---|
| 文本生成 | 5~30s | 边缘可过 |
| **图生图** | **20~60s** | **必然失败** |
| 批量外部 API 调用 | 视批量而定 | 大概率失败 |

在图生图云函数目录下建 `config.json`：

```json
{ "timeout": 300 }
```

**上限说明**：云函数超时是有上限的（本项目用的 300s 已能满足图生图；官方图生图建议区间为 300~900s，具体以当前文档为准）。

**同时要在 UI 上明示预期**。超时 300 秒不等于用户愿意等 300 秒——loading 必须写"最长约 60 秒"这种具体数字。

## 四、环境变量：密钥永远不进源码

**这是整个交付流程里风险最高的一项。**

真实踩到的坑：一个云函数把第三方服务的 Key 硬编码成了"兜底值"（没配环境变量时用它）。这在开发期很舒服，但——

> **工程包是要交给评审/客户的。源码里硬编码 Key，等于把 Key 公开。**

**修法**：

```js
// ❌ 错误：源码兜底 = 公开密钥
const KEY = process.env.SERVICE_KEY || 'sk-realkey-here'

// ✅ 正确：只读环境变量，未配置时明确失败（且让前端能降级）
const KEY = process.env.SERVICE_KEY
if (!KEY) return { error: 'SERVICE_KEY_NOT_CONFIGURED' }
```

配套的两件事：

1. **前端要有降级路径**——云函数返回未配置错误时，功能降级而不是崩溃；
2. **未配置时的表现要写进文档**——因为这种错误往往**不产生异常**（函数正常返回了错误对象），所以**平台的"错误次数"告警发现不了它**，只能靠部署后手动验一次。

**部署后必须手动验证一次**，这是唯一能发现漏配的方式。

## 五、数据库与安全规则

### 5.1 集合规划

这个项目用了 4 个集合：用户投稿、评论、举报记录、全局配置。

**一个可借鉴的简化**：投稿内容（用户发的帖子）与另一种类型的投稿（如成就分享）**存在同一个集合里，用字段区分类型**。好处是审核页只需要查一个集合、翻页逻辑复用、举报关联简化。

### 5.2 安全规则：区分"谁能调"和"调多快"

这是两个完全不同的问题，容易混为一谈：

| 问题 | 手段 | 说明 |
|---|---|---|
| **谁能调** | 云函数权限（安全规则） | 例如拒绝匿名/未登录调用：`auth != null && auth.loginType != 'ANONYMOUS'` |
| **调多快** | 函数内限流 | 安全规则**没有时间维度**，管不了频率 |

**不要以为配了权限规则就防住了刷**——它只保证调用者是本小程序的用户，不保证他不用脚本循环调用。

### 5.3 鉴权只做在服务端

所有写操作在云函数里比对调用者身份，**不要信任前端传来的身份字段**。前端传什么都可以伪造，而云函数运行时注入的身份伪造不了。

### 5.4 管理员权限的"一次认领"模式

需要一个人工审核后台，但不想每次都在控制台改配置。做法：

- 在云函数里存一份管理员名单（数据库配置项）；
- 提供"认领"接口，**仅当名单为空时**接受一次性口令；
- 一旦有人认领，**该口令永久失效**。

这样不需要控制台操作，也不需要长期维护一个口令。

> ⚠️ **这个模式有一个经典的翻车点**，我们真的踩了：如果后台入口用 `wx:if="{{isAdmin}}"` 控制显示，而成为管理员又必须先进后台页输口令——**首次部署时谁都不是管理员 → 入口不出现 → 永远认领不了**，形成死循环。
>
> **修法**：入口条件改为 `isAdmin || !hasAdmin`（没有管理员时也显示，文案改成"认领"），并且 `hasAdmin` 的**初始值必须是 `true`**，避免首屏闪出一个不该出现的入口；云端请求失败时**保持原状态而不是写成 `false`**——否则云端一抖动，所有用户都会看到"认领管理员"入口，后台概念外露。
>
> 详见 [第三册 · 权限与类目合规](../pitfalls/02-权限与类目合规.md)。

## 六、限流：写在函数的最前面

限流的性能位置很关键。这个项目的限流**拦在内容安全检测与入库之前**：

```
进入云函数 → 【限流】→ 内容安全检测 → 写数据库
```

理由：这样超频的请求**消耗不到**内容检测的额度，也不会产生数据库写入。有测试守着这个顺序。

参数按**滥用危害**定，不是按调用成本定：

| 操作 | 分/次 | 天/次 | 为什么 |
|---|---|---|---|
| 评论 | 5 | 50 | 最紧：直接入库、公开可见、没有审核队列兜底 |
| 投稿 | 2 | 10 | 有审核队列兜底，但每次消耗两次内容检测 |
| 生图 | 3 | 30 | 单次最贵（模型配额 + 存储写入） |
| 认领口令 | 5 | 20 | **防口令爆破** |
| 只读默认 | 200 | — | 只挡死循环，正常人翻页碰不到 |

完整实现见 [`tools/cloudfunction-ratelimit.js`](../tools/cloudfunction-ratelimit.js)。

## 七、平台侧告警：期望要放对

**必须澄清一个常见误解**：云开发控制台**没有"每日调用上限"这类硬开关**。平台侧能做的是**提醒**，不是拦截。

能配的：
- **基础告警**：资源使用量达套餐量 80% / 90% 提醒，支持公众号 + 群两种渠道；
- **自定义告警**：指标只有**错误次数**和**运行时间**（没有"调用次数突增"）。

**由此推出的三个结论**（都是查证后才知道的）：

1. **"被刷"平台告警发现不了**——脚本刷出的调用全部成功，错误数为 0；
2. **密钥漏配也发现不了**——未配环境变量时函数是"正常返回错误对象"，不计入错误次数；
3. **阈值取"错误次数 > 2"而非 > 1**——单次偶发（模型抖动、网络瞬断）不值得半夜叫醒。

**所以：函数内限流才是实际防线，平台告警只用于事后发现。**

## 八、部署检查清单

照着勾，别凭记忆：

- [ ] 云函数**逐个**部署，选"上传并部署：云端安装依赖"（首次必须，依赖要在云端装）
- [ ] 所有**新增的模块文件**都随函数上传了（漏传会报"模块找不到"）
- [ ] 使用 AI 能力的函数，`package.json` 里的 SDK 版本满足文档要求
- [ ] 耗时函数已配 `config.json` 超时
- [ ] 需要外部服务 Key 的函数，环境变量**已在控制台配置**
- [ ] 配完环境变量后**手动调用一次验证**（错误会被"正常返回"掩盖）
- [ ] 云函数权限（安全规则）已配置，拒绝匿名/未登录
- [ ] 数据库集合已建，索引按查询字段配好
- [ ] 控制台告警规则已配（基础告警两渠道 + 错误次数策略）
- [ ] 真机走通一遍完整动线（含降级路径）

> **最后一条最关键**：本地一切正常、云端一切正常、但"本地调云端"出问题的情况非常常见——通常是权限、环境变量或版本差异。

## 九、一度判断错的地方

**我以为"平台侧应该能设一个每日调用上限来兜底"。**

实际查证后发现：微信云开发没有这个开关，只有告警。当时用户截图来问"这个上限在哪设"，我第一轮的回答说"在设置里"——**是错的**，第二轮查证后才更正。

**教训**：涉及平台能力边界的问题，**必须以当前官方文档为准去查证**，不能靠"别的平台有所以这个平台应该也有"来推断。而且这类错误如果不主动说明，会一直错下去——所以这篇文档里保留了这个纠错记录。

---

## 一句话小结

> **云开发的便利在于"不用管运维"，代价在于"很多东西你看不见"。**
> 部署清单的价值不是防止打错勾，是强制你把那些看不见的东西（版本、超时、环境变量、权限、告警）逐项确认一遍。
