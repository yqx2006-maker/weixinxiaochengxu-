# 03 · AI 链路接入

## 两条链路，两套失败姿势

| 链路 | 走的通道 | 典型失败 | 兜底 |
|---|---|---|---|
| **文本生成** | 小程序端直连 AI 扩展能力 | 超时、限流（429）、**输出被截断** | 降级本地模板，功能不断 |
| **图生图** | **必须经云函数中转** | 参数契约不符、超时、返回格式不能直接保存 | 返回原图 + 提示，不白屏 |

两条链路有一个共同前提：**它们都可能失败，而且失败是常态而非意外**。整个这一章的设计目标不是"让 AI 更成功"，而是"让 AI 失败时产品依然完整"。

---

## 一、文本链路

### 1.1 调用方式

走平台内置的 AI 扩展能力，好处是**不需要在小程序端存放 API Key**（前端存 Key 等于公开），且与云开发共用一套鉴权。

```ts
// 伪代码：小程序端调用文本模型
const model = wx.cloud.extend.AI.createModel('cloudbase')
const res = await model.generateText({
  model: '<你的文本模型>',
  messages: [{ role: 'user', content: prompt }],
})
```

**关键设计**：把整个调用包在一个**永不 reject** 的函数里。业务层拿到的一定是一个结果对象（成功数据 或 降级数据），而不是一个可能抛出的 Promise——这样页面层不需要写 try/catch，也就不会漏写。

### 1.2 prompt 设计的三件事

**① 强制结构化输出。**

要求模型返回 JSON 数组，**字段名全部给英文并附完整示例**。中文模型对"返回 JSON 数组，形如 `[{ "name": "...", "tags": [...] }]`"这种指令的遵从度，明显高于"返回结构化数据"。

**② 注入有限的业务变量，不要让模型自由发挥。**

风格、人数这类变量不应该写成一大段自然语言描述，而应该是**枚举值 + 对应的一句话约束**。例如：

```ts
// 每种风格给一句"该怎么做"的约束，而不是让模型理解风格名
const STYLE_HINT: Record<string, string> = {
  '随性文艺': '优先选择有质感的小店、旧墙、绿植与光线柔和的角落',
  '城市漫步': '优先选择街道纵深、路牌、天际线与行人流动的场景',
  // ...
}
```

**这一点是被现实教育的**：早期让模型"根据风格名自由发挥"，产出质量极不稳定。

**③ 让模型显式声明它无法被推断的属性。**

这是本项目里最有用的一条经验。

产品需要根据"这个画面该怎么构图"来画不同的示意图。最初的实现是**用关键词从模型生成的文字里反推**构图类型——结果 AI 写的句子一条都不命中规则，所有示意图都退化成同一个默认值。

修法是**双轨判定**：

```
模型显式声明的字段  →  关键词兜底推断  →  默认值
   （最可靠）           （规则要写宽）      （保底）
```

在 prompt 里加一个枚举字段（如 `frameType`，9 个可选值），并要求"不要每个条目都用同一个值"。**让模型做它擅长的事：从有限选项里选一个。而不是让它做它不擅长的事：让下游去猜它的自然语言。**

### 1.3 容错解析：为什么不能直接 `JSON.parse`

模型输出会带这三种表情：

1. 外面包一层 markdown 代码块（` ```json ... ``` `）；
2. **在被截断时给出不完整的 JSON**（这是最致命的——`JSON.parse` 直接抛错，前面生成的内容全部丢失）；
3. 少数情况下带多余的说明文字。

**修法：不要整体解析，要"抢救"。**

```
思路：从字符串里按大括号深度扫描，逐个提取完整的对象；
      能救回几个就救回几个，比整条降级划算得多。
```

需要注意的一个阈值：**如果救回的数量太少，不如整体降级到本地模板**——比如要 8 个条目却只抢救出 2 个，展示 2 个残缺条目比展示 8 个模板条目体验更差。这个阈值是刻意的策略，不是缺陷。

> **注意**：这个阈值后来在一次全项目审核中被误报为"逻辑缺陷"。这类"看起来像 bug 的刻意设计"必须写清楚注释，否则下一个读代码的人（或另一个 AI）一定会把它"修好"。

### 1.4 按需补全：处理部分缺失

模型有时只生成了一部分。与其让用户看到空白，不如**在用户真正打开那一项时按需补一次**。

实现上有四个必须处理的点：

| 注意点 | 原因 |
|---|---|
| **加 in-flight 去重** | 同一个条目被快速点开两次，会发起两次生成 |
| **去重 key 要包含多个字段** | 只用 id 会撞号——AI 生成的内容 id 往往是 `ai_0` / `gen_0` 这类序号，不同批次会重复 |
| **结果写回活动数据并持久化** | 否则下次打开又要点一次 |
| **只持久化"补到的内容"，不要持久化派生内容** | 如果把自己算出来的兜底内容也存下来，下次判断"是否缺失"就永远为 false，**AI 补全再也不会被触发** |

最后一条是真实踩到的坑。它的表现形式很隐蔽：功能"看起来正常"（因为兜底内容填满了），但 AI 补全静默失效了。

## 二、图生图链路

### 2.1 为什么必须经云函数中转

小程序端**不能直连图像模型**。这不是设计选择，是平台约束。所以链路是：

```
小程序端：选图 → 读为 base64 → callFunction
   ↓
云函数：调图像模型 → 拿到结果 → 上传云存储 → 返回 fileID
   ↓
小程序端：downloadFile(fileID) → 得到本地临时路径 → 展示 / 保存相册
```

### 2.2 三个必须查文档确认的点

**① 参数契约要逐字对齐。**

官方文档写的是 `{ model, prompt, images, revise }`，就**只传这四个**。多传可选字段不一定报错，但会静默失效；传了未文档化的字段（例如从别的模型文档抄来的 `enable_thinking` 或 `size`）可能直接报错。

**② 云函数超时必须在配置里显式设置。**

云函数默认超时 20 秒，而图生图 20~60 秒是常态——**默认配置下必然失败**。需要在云函数目录放 `config.json`：

```json
{ "timeout": 300 }
```

**③ 垫图体积上限。**

base64 会让体积涨约 1/3，一定要在**前端读文件前**和**云函数接收后**各做一次体积校验，给出明确提示，而不是让请求超时后才失败。

### 2.3 返回的东西不能直接用（最容易踩的坑）

云函数返回的是云存储的 **fileID**（或临时 https URL）。**这两者都不能直接交给 `<image src>` 和"保存到相册"接口**：

| 用途 | 能否直接用返回值 | 原因 |
|---|---|---|
| `<image src>` | ❌ 视情况 | 用 https URL 受"下载域名白名单"限制，未配置就加载失败 |
| `saveImageToPhotosAlbum` | ❌ **必然失败** | 保存接口**只接受本地路径** |

**正确做法**：拿到 fileID 后先用 `wx.cloud.downloadFile(fileID)` 下载为**本地临时路径**，再展示与保存。用 fileID 走 `downloadFile` 不受域名白名单限制，这是比 https URL 更可靠的一条路。

```ts
// 拿到本地路径才返回给页面
async function toLocalPath(fileID: string): Promise<string> {
  const res = await wx.cloud.downloadFile({ fileID })
  return res.tempFilePath   // 这个才能用于 <image> 和保存相册
}
```

> **这个坑的表现极具误导性**：生成成功、预览失败、保存报错，三件事看起来是三个问题，其实是同一个原因。

### 2.4 云存储的 24 小时时限

云存储的临时链接有时效，所以**不要把临时链接存进用户数据**，要存 fileID，用的时候再换取本地路径。

## 三、降级策略：这一章最重要的一张表

| 风险 | 兜底策略 | 用户感知 |
|---|---|---|
| 文本 AI 超时 / 限流 | 自动降级本地模板，弹窗**如实告知** | 功能不断，知道发生了什么 |
| 单条目内容缺失（输出截断） | 打开时按需补一次；补不到用本地派生内容顶上 | 页面不留白，无感知 |
| 图生图失败 | 返回原图 + 友好提示 | 不白屏 |
| 用户输入的内容无预置数据 | 三级颗粒度模板（通用 / 类目级 / 大类级）补足 | 不出空结果 |
| 云存储图片失效 | 存 fileID，用时换本地路径 | 无感知 |
| 云端完全不可用 | 本地能力全保留（看内容、打卡、出片） | 核心体验不变 |

### 三条设计要点

**① 降级不是静默的。** 降级时要用一句人话告诉用户发生了什么（"云端繁忙，已为你生成备选方案"），而不是假装一切正常。**假装正常会让用户误以为这就是产品的正常水平。**

**② loading 要给出时长预期。** "最长约 60 秒"比一个转圈的菊花有效得多——用户对"知道要等"的容忍度远高于"不知道要等多久"。

**③ 降级路径必须有测试守着。** 否则它会在某次重构中悄悄失效，而且不会有人发现——因为正常路径一直是好的。

## 四、限流：一个必须假设会发生的事

短时间连续生成**一定会**触发限流。这个项目的处理是两层：

| 层 | 做法 | 作用 |
|---|---|---|
| **函数内限流** | 按 openid 做滑动窗口计数 | 挡脚本粗暴刷、保护生图配额（见 [`tools/cloudfunction-ratelimit.js`](../tools/cloudfunction-ratelimit.js)） |
| **平台侧告警** | 控制台配置用量告警 | 事后发现异常 |

**一个必须知道的反直觉结论**：平台侧的**自定义告警指标只有"错误次数"和"运行时间"，没有"调用次数突增"**。也就是说——**"被刷"这件事平台告警发现不了**，因为脚本刷出来的调用全部是成功的，错误数为 0。

所以防刷只能靠函数内限流，不能指望平台告警。

**客户端侧还有一条纪律**：识别到 429 后，**不要把它当成云端故障去熔断**。限流是"你发太快了"的正常反馈，如果按故障处理，会导致整个云端功能被连带冷却——把一个 5 秒的等待放大成一次全面不可用。

## 五、可直接抄的代码骨架

```ts
// ---- 永不 reject 的调用包装 ----
type AiResult<T> = { ok: true; data: T; source: 'ai' } | { ok: false; reason: string }

async function callAiSafe<T>(
  run: () => Promise<T>,
  fallback: () => T,
  timeoutMs = 30_000,
): Promise<AiResult<T>> {
  try {
    const data = await Promise.race([
      run(),
      new Promise<never>((_, rej) => setTimeout(() => rej(new Error('TIMEOUT')), timeoutMs)),
    ])
    return { ok: true, data, source: 'ai' }
  } catch (e: any) {
    // 把降级原因带出去，供 UI 用一句人话告诉用户
    const msg = String(e?.errMsg || e?.message || e)
    return { ok: false, reason: /429|频率|限流/.test(msg) ? 'RATE_LIMIT' : 'FAILED' }
  }
}

// ---- 从被截断的输出里抢救对象 ----
function salvageArray(raw: string): any[] {
  const out: any[] = []
  const start = raw.indexOf('[')
  if (start < 0) return out
  let depth = 0, begin = -1, inStr = false, esc = false
  for (let i = start + 1; i < raw.length; i++) {
    const c = raw[i]
    if (inStr) {
      if (esc) esc = false
      else if (c === '\\') esc = true
      else if (c === '"') inStr = false
      continue
    }
    if (c === '"') inStr = true
    else if (c === '{') { if (depth++ === 0) begin = i }
    else if (c === '}') {
      if (--depth === 0 && begin >= 0) {
        try { out.push(JSON.parse(raw.slice(begin, i + 1))) } catch { /* 跳过这个坏对象 */ }
        begin = -1
      }
    }
    else if (c === ']' && depth === 0) break
  }
  return out
}
```

**注意 `salvageArray` 里 `inStr` 的处理**：不处理字符串内的括号会导致深度计算错乱。这是手写扫描器最常翻车的地方。

## 一句话小结

> **接 AI 的难点从来不在"调通接口"，而在"它失败的时候，你的产品还剩多少"。**
> 把这句话放在设计阶段想清楚，比在演示前一晚发现白屏要从容得多。
