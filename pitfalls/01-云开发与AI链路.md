# 01 · 云开发与 AI 链路

共 11 条。每条格式：**现象 → 根因 → 修法 → 教训**。

（大白话：云开发 = 腾讯帮你管的现成后端；AI 链路 = 把请求发给大模型再把结果给用户的整条路。这 11 条坑全是这条路上摔的，修法都验证过。）

---

## 1. 云函数 SDK 版本过低，直接报错

**现象**：调用云函数里的 AI 图像能力，云函数直接报错，不是降级、不是超时。

**根因**：AI 图像能力依赖云开发 SDK 的较新版本（子依赖需要达到某个最低版本才会挂载相应能力）。`package.json` 里写的是旧版本，能力根本不存在。

**修法**：把 `package.json` 的 SDK 版本提到文档要求的最低版本以上，重新部署（首次必须选"云端安装依赖"）。

**教训**：**接入平台能力前，先读官方文档的「前置条件」章节。** 这类"版本不够就直接崩"的约束文档一定写了，只是通常不在你正在读的那一页。

---

## 2. 云函数默认超时 20 秒，图生图必然失败

**现象**：图生图云函数在本地测试通过，部署后必然失败。

**根因**：图生图单次耗时 20~60 秒是常态，而云函数**默认超时 20 秒**。官方对图生图的建议区间是 300~900 秒。

**修法**：在云函数目录下放 `config.json`：

```json
{ "timeout": 300 }
```

**同时必须在 UI 上明示**："最长约 60 秒"。**超时设置到 300 秒不等于用户愿意等 300 秒**——一个具体的数字比一个转圈的菊花有效得多。

**教训**：**任何"耗时超过 5 秒"的云端调用，都要检查两件事：云函数超时够不够、UI 有没有告诉用户要等多久。**

## 3. 返回的地址不能直接用

**现象**：图生图生成成功、预览失败、保存到相册报错。看起来是三个问题。

**根因**：**这是同一个原因。** 云函数返回的是云存储 fileID 或临时 https URL，而：

| 用途 | 能否直接用返回值 |
|---|---|
| `<image src>` | ❌ 用 https URL 受"下载域名白名单"限制 |
| **保存到相册** | ❌ **必然失败**——保存接口只接受本地路径 |

**修法**：拿到 fileID 后先 `wx.cloud.downloadFile(fileID)` 下载为**本地临时路径**，再展示与保存。

```ts
async function toLocalPath(fileID: string): Promise<string> {
  const res = await wx.cloud.downloadFile({ fileID })
  return res.tempFilePath   // 只有这个能用于 <image> 和保存相册
}
```

顺带记住：**用 fileID 走 `downloadFile` 不受域名白名单限制**，比 https URL 更可靠。

**教训**：**当几个症状同时出现时，先找它们的公共上游，而不是逐个修。** 这里三个症状其实是"拿到的不是本地路径"一件事。

## 4. 云函数之间不能共享模块

**现象**：两个云函数需要同一份业务逻辑，一份放在公共目录里，另一个 `require` 不到。

**根因**：**每个云函数是独立部署单元**，不能跨目录引用。

**修法**：同源复制两份（或引入构建步骤把共享模块复制进各函数目录）。

**要付的代价**：两边不同步就会出现行为不一致，而且**很难被发现**（因为两个函数各自测试都正常）。

**缓解措施**：在文件顶部用醒目的注释写明"本文件与 X 目录下的同名文件必须保持一致，改规则要同步两边"。

**教训**：平台约束下的妥协方案，**必须把它的风险写在代码里**，否则接手的人会以为这是可以随意改的独立文件。

## 5. 密钥永远不进源码

**现象**：为了开发方便，给外部服务的 Key 写了一个"没配环境变量时就用它"的兜底值。

**根因**：**工程源码是要交付出去的。** 源码里的 Key 等于把 Key 公开——而且这种"兜底写法"看起来很方便，很有诱惑力。

**修法**：

```js
// ❌ 错误：源码兜底 = 公开密钥
const KEY = process.env.SERVICE_KEY || 'sk-realkey-here'

// ✅ 正确：只读环境变量，未配置时明确失败
const KEY = process.env.SERVICE_KEY
if (!KEY) return { error: 'SERVICE_KEY_NOT_CONFIGURED' }
```

配套三件事：

1. **前端要有降级路径**——云函数返回未配置错误时功能降级，而不是崩溃；
2. **把"未配置时的表现"写进文档**；
3. **部署后手动验证一次**。

**为什么"部署后手动验证"是必须的**：未配置环境变量时，云函数是**正常返回一个错误对象**——**不产生异常，不计入平台的"错误次数"**。所以告警发现不了它。

**教训**：这是整轮安全审核里危害最高的一项。**判断标准很简单：这个值如果被公开，会造成什么损失？** 只要是"密钥、口令、Key"，就没有任何理由出现在源码里。

## 6. 限流参数应该按"危害"定，不按"成本"定

**现象**：设计接口频率限制时，本能地按"调用一次要花多少钱"来排序。

**根因**：成本视角会算错。举个例子：一条垃圾评论的模型调用成本是 0，但它**直接入库、公开可见、没有审核队列兜底**——危害远高于一次生图（生图贵，但失败了用户只是重试）。

**修法**：按危害排序：

| 操作 | 分/次 | 天/次 | 排序理由 |
|---|---|---|---|
| 评论 | 5 | 50 | **最紧**：直接可见、无兜底 |
| 投稿 | 2 | 10 | 有审核队列，但消耗两次内容检测 |
| 生图 | 3 | 30 | 单次最贵（模型配额 + 存储） |
| 认领口令 | 5 | 20 | **防口令爆破** |
| 只读默认 | 200 | — | 只挡死循环，正常人碰不到 |

**教训**：**"这次调用有多贵"和"这次调用被滥用有多糟"是两个问题，限流要按后者定。**

## 7. 429 不等于云端故障

**现象**：用户短时间连续生成，触发限流（429）。然后**整个社区功能连带不可用了**。

**根因**：客户端把 429 当成普通的云端失败，纳入了**熔断**判定。熔断机制本来是为了防止"云端已经挂了还在反复请求"，结果把一次 5 秒的等待放大成了一次全面不可用。

**修法**：把 429 加入"**不算云端故障**"的白名单，并从中提取"还要等多久"回显给用户。

```ts
const NOT_A_FAILURE = [429, 'TOO_MANY_REQUESTS']   // 限流是正常反馈，不触发熔断
```

用户看到的是"发太快了，12 秒后再试"，而不是"服务暂不可用"。

**教训**：**熔断、重试、降级这些机制，判断条件一定要按"错误性质"分档。** 把所有非 200 都当故障，会把可恢复的正常状态误判为系统故障。

## 8. 平台侧没有"调用上限"这种硬开关

**现象**：想给云函数设一个"每日调用上限"兜底，找不到入口。

**根因**：**这个开关不存在。** 平台侧能做的是**告警**，不是**拦截**。

- **基础告警**：资源使用量达套餐量 80% / 90% 提醒，支持公众号 + 群两种渠道；
- **自定义告警**：指标只有**错误次数**和**运行时间**。

**由此推出的三个结论**（都是查证后才知道的）：

1. **"被刷"平台告警发现不了**——脚本刷出的调用全部成功，错误数为 0；
2. **密钥漏配也发现不了**——未配环境变量时函数是"正常返回错误对象"，不计入错误次数；
3. 告警阈值宜取"错误次数 > 2"——单次偶发（模型抖动、网络瞬断）不值得半夜叫醒。

**修法**：**函数内限流才是实际防线**，平台告警只用于事后发现。

**教训（含一次自我纠错）**：我第一轮回答用户"上限在设置里可以设"，**这是错的**，第二轮查证后更正。

> **凡涉及平台能力边界的问题，必须以当前官方文档为准去查证**，不能靠"别的平台有所以这个平台应该也有"来推断。**而且要主动说明自己改过口**，否则这个错误会一直传下去。

## 9. 告警群建不成，自定义告警就发不出去

**现象**：配置自定义告警时，告警群创建失败（返回 system error，成员列表为空）。

**根因**：自定义告警**只支持"群告警"这一种渠道**（官方口径）。群建不成，自定义告警就没有出口。

**修法**：改用**基础告警**——它在另一个 tab 下，支持**公众号 + 群两种渠道**，公众号那条不依赖群。

**教训**：**配置告警时先确认"发送渠道"可用**，再配置规则。规则配得再细，发不出去等于没配。

## 10. 坐标批量回填会超时，且静默失败

**现象**：一条路线上的机位没有坐标，点导航只弹"暂未收录"。而且**有些路线正常、有些不行**。

**根因**：坐标是在**生成路线时批量回填**的（8 个机位逐个查询），有总超时限制。云函数冷启动 + 逐个查询很容易超时，**失败时静默跳过**——于是那条路线永久没有坐标。

更迷惑的是：开发工具与真机的本地存储**各自独立**，所以"工具里正常、真机不正常"完全可能。

**修法**：把批量回填改成**按需现场补查**：

```
点导航 → 坐标缺失 → 现场查一次（约 2 秒，toast 提示"正在获取"）
       → 成功后写回数据（下次秒开）
       → 仍失败则提示"可到地图手动搜索"
```

**教训**：**"批量预热"看起来优雅，但失败时是静默的。** 对可靠性要求高的数据，改用**按需 + 写回**的模式：单次操作更快、失败可见、且成功后同样是缓存。

## 11. 不是所有数据都该有坐标

**现象**：产品支持"自定义地点"生成路线，兜底模板给出的是"老城街区""城市地标"这类**类别建议**。这些名字被照常丢给地理编码查询——结果命中了同名的小区、商铺甚至外省点位。

**根因**：**类别建议没有唯一位置。** "城市公园"这个词在地图上对应几百个地方。

**修法**：给这类数据打标记，**不回填坐标**；界面上如实说明"这是通用建议点位"，并隐藏"重新查询坐标"按钮（查了也是错的）。

**教训**：**在做数据加工之前，先问一句"这条数据本身有没有唯一解"。** 没有唯一解的数据，任何"精确化"处理都是在制造错误。
