# 08 · 事故复盘

前七篇是"坑与修法"，这一篇是**四次真实事故的完整复盘**。

每一起都造成了实际损失或时间浪费，其中一起**差一点造成不可逆的数据丢失**。

---

## 事故一 · `.git` 被整体删除

**损失**：43 个提交、327 个文件**一度全部不可见**。最终零损失恢复。

**这起事故的价值在于**：它同时暴露了三个平时看不出来的隐患。

### 时间线

```
某日 12:07:41   在 feature 分支上提交了一个检查点
     12:07:42   切换到 main 分支         ← 工作区被整体换成 main 的内容
     12:25       .git 目录被移入回收站
```

### 三个前提（缺一个都不会出事）

| 前提 | 说明 |
|---|---|
| **① 主分支长期未合并** | `main` 停在几天前，全部新工作都在 feature 分支上，两者差了 40+ 个提交 |
| **② 所有开发都在 feature 分支** | 从没有人把成果合并回 `main`，所以 `main` 是一个"看起来很旧"的分支 |
| **③ 某次操作切换了分支** | **切分支 = 工作区文件被整体替换**，不是"看一眼旧版本" |

### 为什么难诊断

进入工作区时看到的是：

```
83 个文件显示为 D（已删除），但工作区文件看起来"还在"
```

**这个组合极其误导**——文件明明在，为什么 git 说是删除？

原因是：**工作区的内容已经被换成了旧版本**，所以和 HEAD 对不上。文件"在"，但内容不是那个提交的内容。

**能救命的判据**：

| `git status` 第一列 | 含义 | 处理 |
|---|---|---|
| 大量 `A` | **引用没被读懂**（编码/格式损坏） | 修引用文件 |
| 大量 `D` | 引用指向旧提交 | 检出到正确提交 |
| 若干 `M` | 工具真的改了文件 | 比对内容 |

### 恢复（简述）

常规手段全部失效后的路径：

1. **先找回收站**——但要注意，回收站里的 `.git` 可能是**空壳**（本次只有 32 个文件、对象目录全空）。**直接还原没用。**
2. **不要依赖回收站的路径元数据**——它记录的原始路径可能被截断（38 位哈希只剩 22 位），无法据此重建结构。
3. **暴力扫内容**：遍历所有候选文件，逐个尝试解压，解压后内容形如 `b"<类型> <大小>\x00..."`，再对内容算哈希与文件名比对，命中即收集。

```
13911 个候选文件 → 2086 个有效对象 → 目标提交及整条祖先链全部命中
```

4. **重建仓库**：按哈希写入对象目录、写引用、校验完整性、检出到工作区。

### 教训

**① 切分支前先确认三件事**：当前分支、目标分支、两者的差距。

**② 主分支不能长期落后。** 每完成一个可交付的里程碑就合并回去——**破坏半径会小很多**。

**③ 定期做整包快照**：

```bash
git bundle create backup/full-<date>.bundle --all
git bundle verify backup/full-<date>.bundle
```

单个文件、可丢网盘、恢复就是完整克隆。**成本几秒，代价是你不会因为一次误操作损失一周。**

**④ 这次能救回来是运气好**——回收站没被清空、对象文件没被覆盖、且有能力识别它们。**三个条件不总是同时成立。**

**⑤ 一个工作区同时只能有一个"写者"。** 切分支、检出、重置、批量删除——都算"写"。

## 事故二 · 工具目录整体消失

**现象**：整理废弃配置时，发现整个工具目录（41 个文件）**从工作区不见了**，其中包括几份"改前备份"。

**损失**：零。**全部文件已入库**，一条恢复命令就全回来了。唯一丢失的是一个未提交的临时配置（事后证明不再需要）。

**为什么零损失**：这是**运气 + 习惯**的组合。习惯是"每天收工前提交"；运气是那天确实提交过。

**成因而未完全定位**——疑似与"批量删除后紧接着批量添加"的时序有关。

### 教训

**① 这次没翻车的唯一原因是"所有东西都已经提交"。**

> 那 41 个文件里如果有**一个未提交的改前备份**，它就永久消失了。

**② 批量删除前的三条纪律**：

- 先确认工作区状态（干净 / 所有改动已提交）；
- 优先用版本控制恢复，而不是"小心别删错"；
- 删除前**先看目标列表**，不要用通配符批量删。

**③ "改前备份"应该进版本控制，而不是放在工作区。** 放在工作区的备份，和工作区里其他文件承担同样的风险。

## 事故三 · 两个 AI 各写了一份服务

**现象**：两个 AI 各自实现了一份功能相同的模块（图像生成服务）。**两份都在，都工作正常。**

**发现方式**：**收工汇报**。一个 AI 在消息里写了"新增 `xxx.service.ts`"，而另一个 AI 刚刚把同样的逻辑写进了另一个文件。因为双方都按规矩汇报了，所以：

```
发现 → 确认 → 删掉重复的一份 → 5 分钟解决
```

### 为什么这类问题最贵

**它不报错。** 两份代码各自都正常工作，测试也都能过。只有当你发现"改了 A 那份，B 那份没变，行为不一致"时才暴露——而那时可能已经过了很久。

**如果没有汇报机制，这两份代码会一起活到交付。**

### 教训

**① 收工汇报是发现重复实现的唯一手段。**

因为"我写了什么"这件事，**只有写的人知道**。不汇报的话，另一个人（或 AI）无从得知。

**② 汇报格式里"是否影响他人"这一栏不能省。**

它强迫汇报者思考一次影响范围。"无影响"和"影响了共享类型定义，请重新编译"是两种完全不同的信息量。

**③ 开工前先读一遍已有代码。**

AI 最大的浪费不是写错，是**写重复**。花 5 分钟读，能省掉一次返工。

## 事故四 · 我的三条"优化建议"里有两条在几何上不成立

**背景**：用户希望调整一个固定尺寸版面的上下比例，我提了三条结构性优化建议。

**结果**：其中**两条在几何上不成立，甚至是反向的**。

| 我的建议 | 为什么错 |
|---|---|
| "把左侧文案从并排改成顶部横排" | 左栏原本与图片**并排**、不占额外高度；改成顶部横排等于**并行变串行**，高度反而增加约 250px |
| "三屏减为两屏" | **同行内少一屏不会让行变矮**（行高由最高那一屏决定），除非缩小剩下的屏——那就又牺牲可读性 |

**根本约束（当时没算清）**：

```
竖屏截图约 2.1:1  →  行高 ≈ 2.1 × 屏宽
```

**"屏更大"与"行更矮"数学上互斥。** 能减高的只有屏宽——这是一道乘法题，不是取舍题。

### 处理方式

纠错，并把三条**真实可行**的路径连同各自的代价摆出来让用户选。

**最终结果**：用户选定了其中一条（合并 + 缩小一档），执行后版面精确贴合。

**期间还发生了 4 轮迭代**（用户逐轮调整比例），每一轮都遵循同一条原则：

> **画布高度固定时，"缩小某处"本质是重分配，不是等比缩放。每次缩完必须立刻把等量高度加到另一处，并保持总高仍贴合画布。**

上下比例的实际演化：`2.41 : 1 → 1.93 → 1.31 → 0.54 → 0.63`。

### 教训

**① 给结构性建议前，先把几何/逻辑模型算清楚。**

"感觉这样能变矮"不是依据。**一道乘法题算错，会让所有建议都站不住。**

**② 提建议时要附带代价。**

不要说"可以合并卡片"，要说"合并卡片能省 X，代价是两栏变一栏后每栏更窄"。**不带代价的建议是不可用的。**

**③ 让用户做选择，而不是替用户决定。**

这次真正推进的是：**把可行路径和各自代价列清楚，让人选**。

## 四起事故的共同结构

把它们放在一起看，会发现一个共同的模式：

| 事故 | 表面原因 | 真实原因 |
|---|---|---|
| `.git` 被删 | 一次切分支操作 | **主分支长期落后 + 没有快照** |
| 目录消失 | 一次批量操作 | **依赖"别删错"，而非版本控制** |
| 重复实现 | 两个 AI 各自实现 | **缺少"我做了什么"的同步机制** |
| 建议错误 | 一次判断失误 | **没算清约束就给结论** |

**四起事故的"表面原因"都是一次具体的操作或判断，但"真实原因"都是缺少一个机制。**

> **一次操作的失误不可避免；一个机制的缺失会让同类事故反复发生。**

所以四条对策都是**机制性**的，不是"下次注意"：

1. 主分支定期合并 + 每天 bundle 快照 → 事故一
2. 批量删除前检查工作区状态 + 优先用版本控制恢复 → 事故二
3. 收工必汇报 + 开工先读 → 事故三
4. 给结论前先算清约束 + 附上代价 → 事故四

## 还有一类"事故"值得记录：判断错误

上面四起是技术事故。**还有一类损失来自判断错误**，它们不产生错误日志，但会浪费大量时间：

| 判断 | 事实 | 处置 |
|---|---|---|
| "平台侧可以设置每日调用上限" | **没有这个开关**，只有告警 | 更正并写进文档 |
| "剪切板这项可以从隐私声明里删掉" | 代码里有**写入**剪切板的操作，而声明对读写都算 | 更正，并改成"写不是读"的澄清口径 |
| "把界面上的 AI 字样去掉就能规避类目限制" | **审核看的是功能实质，不是文案** | 更正，识别出这是"实质合规"问题 |
| "移除全部分享功能就能过审" | **转发小程序本身是基础能力，平台还要求定义它** | 第二轮恢复 4 处 |

### 为什么要把这些写下来

1. **防止重复踩坑**——下一个人（或 AI）看不到纠错记录，很可能重新得出那个错误结论；
2. **它让"正确结论"变得可信**——一份从不犯错的记录，读起来像宣传材料；
3. **它本身就是最好的方法论文档**——"我一度判断错了，这是我为什么改"比"这是最佳实践"更有说服力。

### 教训

> **在不确定的地方，明确说"我不确定，需要查证"，比给一个自信的答案有价值得多。**
>
> 因为这些领域的共同特征是：**答案不在你的常识里，在官方文档里。** 而且不同平台的差异极大、规则还会变。
