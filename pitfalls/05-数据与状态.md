# 05 · 数据与状态

共 8 条。这一篇的共同点是：**数据"看起来是对的"，但在特定路径下会变坏。** 它们全部与"谁能修改这份数据"有关。

（大白话：这一篇讲用户的数据怎么存、怎么改。8 条坑的共同点：平时看着没问题，某条特定路径一走就坏。）

---

## 1. 默认值被就地污染

**现象**：用户清空本地存储后，一个全新用户的档案里**带着旧积分和旧奖章**。

**根因**：

```ts
// ❌ 默认档案是一个模块级常量对象
const DEFAULT_PROFILE = { points: 0, badges: [], stats: {} }

function getProfile() {
  return storage.get('profile') || DEFAULT_PROFILE   // 返回的是【同一个对象的引用】
}

function addPoints(n) {
  const p = getProfile()
  p.points += n          // ← 就地修改
  storage.set('profile', p)
}
```

`addPoints` 修改的是 `DEFAULT_PROFILE` 本身。**几次加分之后，这个"常量"已经面目全非。** 之后任何走到 `|| DEFAULT_PROFILE` 的路径，拿到的都是被污染过的对象。

**修法**：改成工厂函数，每次返回**全新对象**：

```ts
const makeDefaultProfile = () => ({ points: 0, badges: [], stats: {} })
function getProfile() {
  return storage.get('profile') || makeDefaultProfile()
}
```

**这个 bug 是写单元测试时被测试本身抓出来的**——因为测试问了一个问题："这个默认值能不能被修改？"

**教训**：

1. **"默认值"这种东西在语义上应该不可变**，用常量对象实现就有被共享引用的风险；
2. **同一个函数既返回"已有数据"又返回"默认数据"时，两者必须都是新对象**；
3. **这个 bug 展示了测试的真正价值**：不是防回归，是**逼你说清"这个函数的约束是什么"**。

## 2. 累加操作必须幂等

**现象**：同一件事做两次，统计数字被加了两次。

**根因**：完成操作时无条件累加，没有判断"是不是已经完成过"。

**修法**：用**调用前的状态**判断——已经完成的只更新内容，不计数。

**教训**：**每一个"加一"的地方，都要问"这个操作会不会被执行两次"。**

可能的重复来源：网络重试、用户连点、多入口进入、从旧的缓存恢复。**全部是真实会发生的。**

---

## 3. 切换路线时丢进度

**现象**：用户在"历史记录"里点"继续"，**把正在走的这条路线的全部进度弄丢了**。

**根因**：接管新路线时**直接覆盖了"当前路线"这个位置，没有先归档原来那条**。

```
用户正在走路线 A（有 5 个打卡记录）
  → 在历史里点"继续"路线 B
  → 当前位被 B 覆盖
  → A 的进度没了
```

**修法**：接管前**先归档当前路线**。

**一个容易漏的细节**：

> **归档后要重新读一次历史列表**，因为你刚归档的那条可能不在你之前读到的副本里——不重读会把它写没。

**教训**：**任何"覆盖当前状态"的操作，都要先问"原来的状态去哪了"。** 覆盖是最好写的实现，也是最容易丢数据的实现。

## 4. 派生内容被持久化，导致 AI 补全永久失效

**现象**：某功能"看起来正常"（界面有内容），但**它本该触发的 AI 补全从来没有执行过**。

**根因（两步错误叠加）**：

```
① 判断"是否需要补全"的依据，用的是【折算后】的数据
   —— 而折算过程已经把字段填满了
   —— 于是"是否缺失"永远是 false

② 即使触发了补全，也把【派生出来的兜底内容】一起持久化了
   —— 下次判断时同样不为空
```

**修法**：

- 判断依据改用**原始数据**（并排除已有正式内容的条目）；
- **只持久化"真正补到的内容"**，不要把派生内容写回。

**必须加注释说明**：因为"不持久化派生内容"看起来像 bug（明明算出来了为什么不保存？）。

**教训（本篇最重要的一条）**：**"检查缺失"和"填充缺失"必须在不同的数据视角上进行。**

> ```
> 用 A 判断 → 对 A 填充 → 存 A
> ```
> 那么 A 永远不为空，检查逻辑**只会在第一次生效**。

## 5. 旧数据折算时把同一句话抄进了两个地方

**现象**：用户反馈——两个版本的内容**点开关切换后一模一样**。

**根因**：旧版数据只有一组三个字段，折算到新版的两个版本时，代码把**同一句话同时写进了两个版本**。

**修法**：明确归属 + 派生补齐：

```
旧字段措辞偏专业 → 只归【专业版】
另一版 → 用本地派生内容补齐（含真实信息，但不能与专业版撞句）
```

**并且加一条硬约束**：**同一句话不得同时出现在两个版本里**（由脚本守着）。

**教训**：**数据迁移时，"两个新字段该填什么"必须有明确规则，不能因为"反正都有值"就复制。** 复制出来的两个字段看起来完整，实际意味着一个版本是废的。

## 6. 数据已经坏掉了，修代码不会修数据

**现象**：修复了一个数据加工的错误，但**用户的设备上显示的还是错的**。

**根因**：错误数据已经写入用户的本地存储。**修代码只影响之后新生成的数据。**

**修法**：明确告知用户/使用者——**需要重新生成一次**才会走新逻辑。

**教训**：**修数据加工逻辑时，永远要问一句"已经产生的数据怎么办"。** 三个选项：

| 选项 | 适用 |
|---|---|
| 提示用户重新生成 | 数据可再生（如 AI 生成的内容） |
| 写一次性迁移脚本 | 数据不可再生（如用户自己输入的） |
| 静默兼容（读取时识别并修正） | 影响面广、不想打扰用户 |

**选错会得到一个尴尬的结果**：代码是对的，用户看到的是错的。

## 7. 云端失败时把状态写成了"没有"

**现象**：云端一抖动，**所有用户**都会看到一个本该只有管理员能看到的入口。

**根因**：

```ts
const who = await callCloud()          // 云端不可用时返回 null
setData({ hasAdmin: !!(who && who.hasAdmin) })
//                          ↑ null 时被写成 false
```

**"未知"被当成了"否"。**

**修法**：**拿不到结果就保持原状态，不要写。**

```ts
const who = await callCloud()
if (!who) return                        // 保持原状态
setData({ hasAdmin: !!who.hasAdmin })
```

并且初始值要设成**安全态**（本项目里是 `true`：既不显示管理员入口，也不显示认领入口）。

**教训**：**三态数据不要压成两态。** "是 / 否 / 不知道"里，"不知道"必须有独立的处理分支——把它归入"否"会造成误判，归入"是"会造成权限外露。

## 8. 本地数据结构漂移

**现象**：读本地存储时拿到 `undefined`，页面显示空白或崩溃，**没有任何报错**。

**根因**：本地存储存的是序列化对象，**没有任何 schema 约束**。改了结构、加了字段、改了字段名之后，老数据读出来就是这样。

**修法**：

1. **用 TypeScript 定义存储结构**，读写都过一遍类型；
2. **读取时统一做归一化**（缺字段就给默认值）；
3. **加版本号**，为将来的迁移留出判断依据。

**教训**：**本地存储是"没有服务端校验的数据库"。** 所有你在服务端会做的防护（字段兜底、版本迁移），在本地存储这里一件都不能少。

## 一条跨篇的元规律

这一篇的问题有一个共同结构：

> **某份数据被多个代码路径访问，而只有一条路径做了正确的事。**

- 默认值：多个地方读，只有一处会改；
- 归档：多处切换路线，只有一处会归档；
- 派生内容：多处判断缺失，都在看被填满的那份数据；
- 三态：只有一个分支处理了"不知道"。

**所以排查数据类 bug 的一个高效方法是：把这份数据的所有读点和写点列出来，然后逐个检查它们对"边界状态"的处理是否一致。**
