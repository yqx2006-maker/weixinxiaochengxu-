# 03 · 真机与调试

共 12 条。这一篇的共同点是：**在开发者工具里一切正常，真机上出问题。**

（大白话：真机 = 真实手机。模拟器里好好的、手机上一跑就崩的问题全在这——这类问题占了我们全部 bug 的三成以上。）

---

## 1. 真机与开发工具的本地存储是两套

**现象**：某些功能在开发者工具里完全正常，真机上就是不работ；且**同一条数据、同一份代码**，两边表现不同。

**根因**：**开发者工具与真机的本地存储相互独立。** 在工具里生成的路线、打卡记录、缓存，真机上一份都没有。

**实际影响**：项目里有一个"坐标回填失败就静默跳过"的缺陷，在工具里恰好成功过一次，数据留在工具的存储里；而真机上那次生成恰好失败，于是**该路线永久没有坐标**。表现为"工具里好好的，真机不行"。

**修法**：
- 排查任何真机问题时，**先确认这份数据是怎么来的**（真机自己生成的？还是从工具同步的？）；
- 需要复现时，**在真机上重新走一遍生成流程**，不要依赖工具里的数据。

**教训**：**"我这里能跑"这句话，在小程序开发里价值接近于零。** 从项目第二天起就建立"每天真机走一遍主链路"的习惯。

---

## 2. 模拟器里的组件只是模拟

**现象**：某个组件在工具里显示正常，真机上行为完全不同。

**根因**：像原生取景这类组件，在开发者工具里**显示的是模拟画面**，不是真实相机流。

**修法**：这类功能只能在真机上验证。**在任务清单里明确标注"此功能需真机验证"**，不要把它算作"已完成"。

**教训**：**区分"代码写完了"和"功能验证过了"。** 前者是 AI 能帮你确认的，后者只有真机可以。

---

## 3. 生成完成后落在了错误的页面

**现象**：用户完成一次生成后说"**没有总的路线**"——他只看到一列任务，没有全局视图。

**根因**：生成完成后，代码直接跳转到了**任务清单页**（用 `switchTab`），**跳过了唯一的总览视图**（有路线说明 + 时间轴 + 地图入口）。而任务页本身**没有任何通往总览的入口**。

**两个错误叠加**：

1. 落点选错了（跳过总览）；
2. **总览视图没有其他入口**——如果任务页有这个入口，用户也能自己找到。

**修法**：

```
① 落点改为总览页（跳转失败时兜底回任务页）
② 任务页顶部补一个"查看总览"卡片
```

**教训**：**"信息的唯一入口"是危险设计。** 任何一个重要视图，都应该至少有两个入口。这样即使某个跳转逻辑有 bug，用户也不会完全找不到它。

---

## 4. 返回行为应该按来源决定

**现象**：从任务详情页点"回路线看看"，有时返回上一页更自然，有时应该跳到路线详情页。

**根因**：同一个按钮，用户可能从两个地方进来（从总览页进来 / 从任务页进来）。固定的跳转方式总有一半是错的。

**修法**：记录来源，按来源决定行为——**从总览页进来的就后退，从任务页进来的就跳到总览页**。

**教训**：**当同一个入口有多种来路时，"返回"的语义就变得不唯一。** 这类问题在真机上感受特别明显（用户会觉得"怎么绕回来了"）。

---

## 5. 地图画出一条荒谬的路线

**现象**：用户真机反馈——地图页显示相邻两点相距 **103.6 公里 / 101.8 公里 / 22.6 公里**。

**根因**：AI 生成失败时降级到通用模板，机位名是"老城街区""城市地标""本地市场""城市公园"这类**类别建议**。而坐标回填逻辑**照常把它们丢给地理编码去查**：

```
"城市 · 老城街区" → 去掉城市前缀 → 搜 POI"老城街区"
                  → 命中同名小区/商铺/外省点位
                  → 坐标散落上百公里
```

**修法（4 处改动）**：

```
① 数据结构加标记 generic（通用建议机位，无唯一位置）
② 生成通用模板时统一打上标记
③ 坐标回填【跳过】带标记的机位
④ 界面如实说明"这是通用建议点位"，并【隐藏"重新查询坐标"按钮】
   ——因为查了也是错的
```

**顺带暴露的项目事实**：这一条同时暴露了"预置机位只覆盖 2 个城市，其余城市池子为空，AI 一失败就必然退到通用模板"——**修完这个坑，还要补内容库，否则同一个问题会换个形式再出现。**

> **注意**：用户手机上那条旧路线**已经写入了错误坐标**，必须**重新生成**才会走新逻辑。这类"数据已经坏掉"的坑，修代码不会自动修数据。

**教训**：
1. **在做数据加工前先问"这条数据本身有没有唯一解"**；
2. **修一个 bug 时，顺手问"数据源头是不是也有问题"**——否则修的是症状。

## 6. "换一张"点了没反应

**现象**：已经打卡的站点，点"换一张"选完照片后**什么都没发生**，新照片静默丢失。

**根因**：选完照片后，照片被写进"待确认"状态；但**确认按钮只在"未打卡"的分支里渲染**——已经打卡的站点走的是另一个分支，那个分支上根本没有确认按钮。

于是：**操作完成了、数据写进去了、但没有任何东西能消费它。**

**修法**：选图逻辑加"替换"分支——已打卡时，选完直接完成替换，不走确认流程。

**教训**：**"操作后没有可见反馈"是最难自己发现的 bug 类型**，因为代码不报错、日志没有异常、状态也确实变了。**发现它的唯一方式是真机把每条路径走一遍**——包括"重复操作已经完成的事情"这条路径。

---

## 7. 打卡统计被重复计数

**现象**：同一站点重复打卡，照片数量和任务完成数被重复累加。

**根因**：完成操作时无条件调用统计累加，**对"已经完成"的状态没有保护**。

**修法**：用**调用前的状态**判断——已经完成的站点只换图，不计数。

**教训**：**所有"累加"操作都要问一句"这个操作会不会被执行两次"。** 幂等性不是可选项。

---

## 8. 云端数据缺字段，把页面搞崩

**现象**：云端返回的帖子数据点"加入某处"时崩溃。

**根因**：代码直接访问了 `data.tips[0]`。而**云端数据的字段可能缺失**（不同版本发布的帖子、或发布时字段为空）——`undefined[0]` 直接抛错。

**修法**：

```ts
const tips = d.tips || []          // 不假设字段一定存在
const name = d.title || ''         // 字符串字段也要有兜底
```

**教训**：**永远不要假设云端返回的数据符合你的类型定义。** 类型是前端写的，数据是数据库给的，两者之间没有强制约束。**所有来自网络/数据库的字段，读取前都要兜底。**

---

## 9. 跨批次的数据撞号

**现象**：并发补充某类内容时，数据"串味"——A 批次的内容被写到了 B 批次的条目上。

**根因**：去重 key 只用了一个 id 字段。而 AI 生成的内容 id 往往是 `ai_0` / `gen_0` 这类**按序号生成的 id**——**不同批次会重复**。

**修法**：key 改为多字段组合（如 `${id}|${name}`）。

**教训**：**"序号型 id"不是唯一标识。** 任何时候用 id 做 key、做缓存、做去重，都要确认它在**全局**唯一，而不只是在自己这一批里唯一。

---

## 10. 奖章/成就被提前解锁

**现象**："完成 N 条路线"类的成就在数量不够时就解锁了。

**根因**：统计时把"历史路线"和"当前进行中的路线"**相加**，而**走完的路线同时存在于这两个列表里**——于是被算了两次。

**修法**：按 id **去重后再计数**。

**教训**：**两个数据源合并统计时，第一件事就是检查重叠。** 尤其是"历史"和"当前"这种天然会有交集的划分。

---

## 11. 输入框里的文字被压缩裁切

**现象**：真机上输入框的标签和文字显示不全，被压扁。

**根因**：只设了内边距，没有显式指定**高度与行高**。不同机型/版本下，控件的默认高度计算不一致，内边距把内容挤掉了。

**修法**：显式写死

```css
.input {
  height: 88rpx;
  line-height: 88rpx;   /* 必须与 height 一致 */
  padding: 0 24rpx;     /* 水平内边距，垂直交给 height */
}
```

**教训**：**表单控件的样式要"写死"，不要依赖默认值。** 这是少数值得放弃一点灵活性的地方。

---

## 12. "云服务繁忙"背后的真实原因

**现象**：生成时报"云服务繁忙"并降级。

**根因**：文本模型返回了 **429（频率限制）**——短时间反复生成触发的。前端的错误映射把非预期的错误统一显示为"云端服务超时"或"繁忙"，**掩盖了真实原因**。

**修法**：

1. 错误提示里带**原因**（弹窗第二行显示原始错误信息）——这是最准的诊断入口；
2. 对 429 做专门识别，给出"发太快了，X 秒后再试"这种**可执行**的提示；
3. **不要把它和"云端故障"混为一谈**（见 [01 篇第 7 条](01-云开发与AI链路.md#7-429-不等于云端故障)）。

**教训**：**错误提示要能诊断，不能只是"出错了"。**

一个好的错误提示应该让用户（或开发者）**知道下一步做什么**：
- "没网了，检查一下连接"（可执行）
- "服务暂不可用"（无从下手）

---

## 一条跨篇的元规律

这一篇里的问题有一个共同特征：**它们都不是"代码错了"，而是"某条路径没有被走到过"。**

```
新装用户的路径           ← 默认值问题
重复操作的路径           ← 幂等性问题
从另一个入口进来的路径    ← 返回行为问题
云端返回不全的路径       ← 字段兜底问题
数据已经坏掉的路径       ← 修复不会回溯修数据
```

**所以真机测试不能只走"正常流程"，要专门走这些路径**：

- [ ] 全新用户（清空存储）走一遍
- [ ] 重复操作已经完成的事
- [ ] 从每个可能的入口进入同一页面
- [ ] 断网 / 弱网下操作
- [ ] 用一条"以前生成的老数据"走一遍
