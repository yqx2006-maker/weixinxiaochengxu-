# 06 · 内容质量与 AI 输出

共 8 条。这一篇讲的是**用 AI 生成面向用户的内容**时会发生什么，以及怎么用机器守住质量。

---

## 1. 输出被截断，整条降级把前面的成果也丢了

**现象**：AI 返回的内容太长时被截断，导致**整批内容降级到本地模板**——明明前几个条目已经生成好了。

**根因**：解析用的是整体 `JSON.parse`。**截断的 JSON 解析直接抛错，前面的内容一起丢掉。**

**修法**：**改成"抢救式解析"**——从字符串里按大括号深度扫描，逐个提取完整的对象，能救回几个算几个。

```ts
function salvageArray(raw: string): any[] {
  const out: any[] = []
  const start = raw.indexOf('[')
  if (start < 0) return out
  let depth = 0, begin = -1, inStr = false, esc = false
  for (let i = start + 1; i < raw.length; i++) {
    const c = raw[i]
    if (inStr) {                       // ← 这个分支不能省
      if (esc) esc = false
      else if (c === '\\') esc = true
      else if (c === '"') inStr = false
      continue
    }
    if (c === '"') inStr = true
    else if (c === '{') { if (depth++ === 0) begin = i }
    else if (c === '}') {
      if (--depth === 0 && begin >= 0) {
        try { out.push(JSON.parse(raw.slice(begin, i + 1))) } catch {}
        begin = -1
      }
    }
    else if (c === ']' && depth === 0) break
  }
  return out
}
```

**手写扫描器最容易翻车的地方是字符串处理**：如果不处理字符串内部的括号（`inStr` 分支），深度计算会错乱，解析结果不可预测。

**还要设一个"下限阈值"**：如果只抢救出 2 条而预期是 8 条，**不如整体降级**——展示 2 条残缺内容比展示 8 条模板内容体验更差。

> ⚠️ **这个阈值在后来的项目审核中被误报为"逻辑缺陷"。** 这类"看起来像 bug 的刻意设计"**必须写清注释**，否则下一个读代码的人一定会把它"修好"。

**教训**：**处理不可靠输出时，"部分成功"通常优于"整体失败"**——但要判断"部分成功"是否已经差到不如不用。

## 2. 关键词兜底规则太窄，所有内容都落到默认值

**现象**：界面上每组内容的示意图**完全相同**（都是默认样式）。

**根因**：示意图的类型是**用关键词从 AI 生成的文字里反推**的。而规则只有 6 组很窄的关键词：

```
分居左右 / 深处 / 画面上方 / 下半张 / 一侧 / 占满
```

AI 实际写出来的句子（如「…手机横举齐眼朝里，两人背影入画」）**一条都不命中**：

- "左侧"不等于"偏左"；
- "两人入画"完全没被覆盖。

于是**整条数据每一组都落到默认值**。

**修法：改成三层判定，先准后宽**

```
① 让模型显式声明类型（枚举值，最可靠）
      ↓ 缺失时才往下走
② 关键词推断（规则扩到 8 组，覆盖方位词/主体形态/纵深/上下）
      ↓ 都不命中才
③ 默认值
```

同时新增两种此前缺失的类型（"两人并排""凑近特写"），并同步补齐界面分支。

**效果**（用脚本实测）：预置内容从"全部默认"变为 **5 种类型**分布。

**教训**：**不要让下游去猜上游的自然语言。** 让模型做它擅长的事——**从有限选项里选一个**——而不是让它写散文，再让你用正则去理解它。

## 3. 重建对象时丢新字段

**现象**：**所有生成的数据都缺一个字段**，而预置数据单独检查时是好的。

**根因**：有一个"按条件补提示"的函数，内部**重建了整个对象**：

```ts
// ❌ 只复制了当时已知的字段
return { ...spot, shot: { easy: shot.easy, pro: shot.pro } }
```

后来给数据结构新增了一个字段（`first`），但**这个重建点没有更新**——新字段被丢掉了。

**为什么难发现**：预置数据不经过这条重建路径，所以单独检查预置数据完全正常。**只有生成的数据缺字段。**

**修法**：

```ts
return { ...spot, shot: { ...shot, easy, pro } }   // 展开原对象，保留全部字段
```

**教训（本篇最实用的一条）**：

> **任何"重建一个对象"的地方，都要过一遍全部字段。**
>
> 更彻底的做法是**避免重建**——只改动需要的字段，其余保持原引用。重建是丢字段 bug 的主要来源。

**并且**：把新增字段设为**必填**，能让编译器一次性报出所有需要补齐的位置。这一步救了后面所有的字段新增。

## 4. prompt 里的示例和约束自相矛盾

**现象**：同一个 prompt 里，一边要求"绝不编造距离"，一边在示例里写了一个带距离的句子。

**根因**：示例是早期写的，后来加约束时**忘了改示例**。

**模型会学示例，不会学规则**——所以它会照着示例编造距离。

**修法**：删掉示例里的距离描述，并**把约束和示例放在相邻位置**，改的时候能一起看到。

**教训**：**prompt 里的示例是"强规则"，约束是"弱规则"。** 两者冲突时，模型跟示例走。所以**改约束时必须同步审一遍示例**。

## 5. 用脚本守内容纪律（四条可抄的规则）

面向用户的内容，靠人审是审不住的（项目里最终有 200+ 条内容，还会反复重写）。做法是把纪律写成脚本。

**四条实际使用的规则**：

| 规则 | 检查方式 | 为什么需要 |
|---|---|---|
| **不得出现专业术语** | 正则匹配术语词表 | 目标用户看不懂"三分线""测光" |
| **不得编造距离** | 匹配"数字 + 米" | 派生场景下不知道具体地点，编数字等于教用户走错路 |
| **方位必须含可数锚点** | 匹配"入口/桥/转角/尽头…" | "堤边"这种方位站哪儿都成立，无法执行 |
| **两个版本不得撞句** | 字符串比对 | 撞句 = 其中一个版本是废的 |

再加一条**空话检查**：禁止"随心所欲""随便拍拍"这类放到任何场景都成立的句子。

**关键实现细节**：**逐条打印、不中断**。

```ts
const bad = rows.filter((r) => r.problems.length)
console.log(`检查 ${rows.length} 条内容，不合格 ${bad.length} 条\n`)
for (const r of bad) {
  console.log(`✖ [${r.group}] ${r.name}`)
  for (const p of r.problems) console.log(`    · ${p}`)
}
```

**为什么这个细节重要**：断言式测试在第一条失败时就停了，你只能一条一条改；扫描式脚本**一次列出全部问题**——铺开改 200 条内容时，效率差好几倍。

**教训**：**"要保证质量"是形容词，"跑这条命令看到 0 个不合格"是动作。**

## 6. 事实核查：修正 3 处、删除 1 条

**做法**：所有引用外部事实的内容（开放时间、花期、建筑数量、限流规则…）**逐条去官方来源核对**。

**实际结果**：

- 逐条标注来源，**评审可当场核对**；
- 核对 12 个地点的官方页面；
- **修正 3 处口径不符**——例如"赏枫最佳时间"与官方口径不一致、"盛花期"的截止时间写错了、"建筑栋数"写错了；
- **删除 1 条查无出处的传言**（一条看起来很常见、但找不到任何官方来源的规则）。

**为什么值得花这个时间**：**工具型产品最容易在"内容是否可信"上翻车。** 用户照着你的内容跑一趟，发现是错的，之后所有内容都不被信任了。

**教训**：

1. **"网上都这么说"不等于"有出处"**——一条内容如果一个官方来源都找不到，删掉比留着安全；
2. **数字类内容最容易错**（时间、数量、距离），要重点核；
3. **把来源写在内容旁边**，比写在文档里更有价值——**它让信任可验证**。

## 7. 不要编造互动数据

**做法**：产品里**没有**点赞数、粉丝数、关注按钮。收藏状态和评论数**全部来自用户本人的真实操作**。

**为什么**：编造的数字会让整个产品失去可信度——一旦用户发现某个数字是假的，他会怀疑所有的数字。

**教训**：**设计"看起来热闹"的功能时，先问这个数字从哪来。** 如果没有真实来源，宁可不做这个功能。

## 8. 输出变长会略微增加超时概率，但不会造成限流

**现象**：给 prompt 加了新字段后，出现了"生成失败"。

**当时的怀疑**：是不是 prompt 改动导致的限流？

**实际结论（值得记的判断方法）**：

| 影响 | 是否存在 | 量级 |
|---|---|---|
| 输出变长 → 耗时增加 → **超时概率上升** | ✅ 存在 | 输出各长约 10~15%，**只是略微增加 30s 超时的概率** |
| 输出变长 → **触发限流** | ❌ **不存在** | 限流是按**调用次数**算的，与单次输出的长短无关 |

**真实原因**：短时间反复生成触发了限流。

**教训**：**区分"超时"和"限流"这两种失败**——它们的现象都是"生成失败"，但原因和对策完全相反：

| 失败 | 原因 | 对策 |
|---|---|---|
| **超时** | 单次耗时太长 | 提高超时上限、优化 prompt 长度 |
| **限流** | 短时间调用太多 | 降低频率、加限流提示 |

当时的处理是：**让错误提示带上原始错误信息**——这是最准的诊断入口，比猜快得多。

## 一条跨篇的元规律

这一篇的所有问题都可以归为一句话：

> **AI 输出是不可信输入。**

它可能截断、可能缺字段、可能编造、可能自相矛盾、可能与你的规则冲突。所以围绕它的每一层都要做两件事：

1. **假设它会坏**——容错解析、字段兜底、降级路径；
2. **用机器验证结果**——脚本扫描纪律、逐条核对事实、量化检查（而不是"看起来对"）。

**并且记住：人对 200 条内容的质量判断是不可靠且不可持续的。** 把纪律写成断言，是唯一能规模化的方式。
